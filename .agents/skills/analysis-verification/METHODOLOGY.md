# 分析结论错误的分类学 —— 审查判据

审查一份恶意样本分析报告时，「事实在不在报告里」和「事实对不对」是两个完全不同的问题。
本文件定义**后者**的判据：一份静态分析报告能以哪些方式出错，每一类如何在报告中辨认，以及
每一类必须拿到什么才算被证伪或证实。

判据来源有三处，缺一不可：

1. **本项目实际发布的报告里已经出现过的错误**（每条判据都标了实测出处）。
2. `peinfo` skill 的归因纪律 —— 「不在某个公开 IOC 列表里」永远不能作为归属论据；要主张归属
   只能给正面证据；样本 `source` 必须写清来源。它记录的那次误归因（MD5 `61110bea` 被判为
   「未公开的 Slingshot 用户态核心 RAT」，唯一理由是「不在 Kaspersky 公开的 5 个 MD5 里」，
   实际与本地语料 `DoubleFeatureDll.dll.unfinalized` 逐字节相同）就是 EC-1 的教科书案例。
3. 《恶意代码分析实战》对静态/动态证据等级与常见误判的论述（见
   `sikorski-practical-malware-analysis` skill）。

## EC-1 把「缺席」当成「证明」（misattribution）

**错误形态**：因为某个公开 IOC 列表 / 家族特征库 / 杀软命名里没有这个样本，就断言它属于（或不属于）
某个家族。或反过来：因为样本里有某个家族用过的字符串，就断言归属。

**报告里的辨认特征**：

- 「不在……列表中」「未命中……特征库」「公开情报未见」后面直接接归属结论。
- 归因段落里只有否定证据，没有任何正面证据（内部名 / 独有常量 / 协议魔数 / 构建指纹）。
- 家族名出现在结论里，但同一个家族的**可验证正面特征**在报告别处找不到。

**证实 / 证伪所需**：归属主张必须能指出至少一条正面证据，且该证据在报告中有可回溯的锚点。
拿不到就只能是 `UNKNOWN(attribution)`，不能写成倾向性结论。

**实测出处**：`peinfo` 记录的 `61110bea` 误归因（本地语料 30 秒查询即可推翻）。

## EC-2 把「文件里存在」当成「代码在用」（string ≠ behaviour）

**错误形态**：某个字符串在样本字节里存在，就被写成该样本的行为。典型：把版本资源里的产品名写成
样本身份，把诱饵文件名写成它会创建的文件，把 `schtasks` 这个子串写成它会创建的计划任务。

**报告里的辨认特征**：

- 行为句的主语是样本，宾语是某个字符串，但中间没有「哪个函数消费了它」。
- 同一段里既说「未恢复到消费者」又把它列进能力清单。
- `检测规则建议` 里出现仅供存在性匹配的字符串，却被当成行为指标复述。

**证实 / 证伪所需**：要写成行为，必须给出**消费者**——调用点、参数位、寄存器来源、或对象级使用链。
给不出就只能写成「镜像内字符串线索」，并明确标注它不构成行为。本项目已有一条正确的写法可以对照：
结论摘要里 `FoxitPDFReader.exe` 被写成「镜像内字符串线索，未恢复到对应的进程创建参数，因此不能当作
已恢复的命令行」——这是 EC-2 的正面样板。

**实测出处**：`.data/logs/composed-report.md` 结论摘要的 `FoxitPDFReader.exe`（正确写法）与
字符串事实段（把 `explorer.exeInitializeProcThreadAttributeList failed…` 整段当成一个
「执行相关 API 名称」罗列）。

## EC-3 把散落的事实错误地连起来（wrong join）

**错误形态**：两个事实各自为真，报告把它们连成一个因果/参数关系，但连法没有证据。静态分析里最常见
的三种连错法：

1. **调用点 ↔ 参数**：把某个调用点附近的常量当成该调用的参数，实际它属于相邻的另一次调用。
2. **写入 ↔ 持久化**：见到 `RegSetValueExW` 就写成建立持久化，但没有键路径与值名的 join。
3. **URL ↔ 参数位**：见到 URL 字符串和 WinHTTP 导入就写成「下载该 URL」，但没有 URL 落到
   `WinHttpOpenRequest`/`WinHttpSendRequest` 的参数位。

**报告里的辨认特征**：

- 一条机制写满了输入/输出，但「变换/控制」一栏是空的或写着 `UNKNOWN`，结论却已经下了。
- 参数值被引用，但没有它的来源指令（哪条 `LEA`/`MOV` 把它放进那个寄存器）。
- 机制声明的调用点地址与它引用的参数来源地址不在同一个函数窗口内。

**证实 / 证伪所需**：join 必须能落到**同一函数窗口内的指令级证据**上。本项目对这条已经踩过坑：
`recover_process_creation_arguments` 需要 thunk 映射 + 寄存器追踪，只有 `strings_by_address` 命中
不足以写成参数。拿不到就写 `UNKNOWN(槽位)` + 具体卡点（哪条指令、缺什么），禁止用套话收尾。

**实测出处**：round 72-75 的注册表 join（`RegSetValueExW` 与键名各自存在、join 缺失）；
round 75 记录的 `lpValueName` UNICODE_STRING 间接寻址——**故意不猜**，这正是 EC-3 要求的纪律。

## EC-4 上限/预算造成的静默截断被读成完整清单

**错误形态**：报告里的一个清单是**有上限的**，但正文没有任何地方说明它有上限，读者会当成全集。
这类错误不体现在任何单条事实上——每条都真，但「完整性」这个断言是假的。

**报告里的辨认特征**：

- 段首写「全部」「完整」「所有」，而对应的投影代码里有 `[:N]`。
- 计数与实际列出的条数不一致（例如写「共 N 项」但只列了 M < N 项，且没解释差额）。
- 同一份报告里两处对同一集合给出不同规模，且没有一处说明筛选条件。

**证实 / 证伪所需**：清单要么给全，要么把边界写在正文里（列出条数 + 集合总数 + 差额去向）。
本项目 round 77-78 建立了正确写法可以对照：

    导入表模块清单（7 个）：`advapi32.dll`（3）、`api-ms-win-core-synch-l1-2-0.dll`（3）、
      `kernel32.dll`（95）、`msvcrt.dll`（28）、`ntdll.dll`（5）、`shell32.dll`（1）、`user32.dll`（1）
    边界：以上为按模块归并后的行为相关导入 19 条，PE 导入表共 136 条（差额为 CRT/运行时符号…）

3+3+95+28+5+1+1 = 136，读者可以自己核对；这就是「有上限但不骗人」的形态。

**实测出处**：round 77 的 `imports[:80]`（丢 56 条却读作完整）；
round 78 的「按原样发布（未改写、未截断）」实际只列 13/2423 条。

## EC-5 自己给出的 IOC / 规则无法识别本样本（broken indicator）

**错误形态**：报告生成了可部署的 IOC 或检测规则，但把**不是样本属性**的值标成了样本属性。
最严重的一种：把「计算出来的摘要」当成文件哈希。计算摘要（资源 payload 的 sha256、函数指纹、
规则名后缀）与文件身份哈希没有任何关系，标成 `sha256` 之后这条规则永远匹配不到本样本，
却会被当成「已确认的 IOC」部署出去。

**报告里的辨认特征**：

- YARA rule 的 `strings:` 里有 `// sha256` 注释的条目，其值与样本的 `file_identity.sha256` 不同。
- 同一个 64 位十六进制值在报告里出现两次，一次标 `sha256`（IOC），一次是某资源的摘要。
- 规则里声明的 `url` / `ipv4` / `registry_subkey` 值在样本字节里做原始匹配时不存在
  （值经过了归一化、拼接或截断）。
- 规则名后缀等于规则体内某个 `sha256` 值的前 16 位——规则名是自指的，不是样本指纹。

**证实 / 证伪所需**：每条声明的指标都要能回答「用这条指标去样本里搜，搜得到吗」。
文件哈希类指标必须等于 `file_identity` 记录的值；资源/函数摘要必须**不**以 `sha256` 名义出现在
规则里，或明确标注为「该资源的摘要，非文件哈希」。

**实测出处**：`.data/logs/composed-report.md` 的 YARA 规则同时踩中三条——
`$s0 = "0b05c0df699028e6cfc4c02147e91b7a4ecbc79569004caaf550ebcdb25c63a3" // sha256`
实为规则名后缀（自指），`$s5 = "168d16f9…" // sha256` 实为 `RT_ICON[5]` 的 payload 摘要，
而样本真实 SHA256 是 `6bb6bfcbe68de69077b567789d5970c6613b1d4fb89becc4cf7a2f9a49861145`。
24/24 的存在性验收**完全看不见这个错误**，因为两个字符串都确实在报告文本里。

### EC-5 的复发形态：用「子串」判断来源（substring provenance）

同一个错误在 2026-09 以新形态复发，值得单独记下来，因为它**在修复之后**才出现，而且比原形更难看见。

**错误形态**：「这个摘要是不是文件哈希」这个问题，用**子串包含**来回答：

```python
_FILE_HASH_SOURCES = ("file_identity", "artifact")
def _is_file_hash_source(source): return any(m in source.casefold() for m in _FILE_HASH_SOURCES)
```

`investigation/decoded_artifact` 含子串 `artifact`，于是被判为文件身份。实测于白象样本
`64da3378`（task `0da01730`）：发布出去的 YARA 规则里有 6 条 `// sha256`，其中 5 条是解码载荷摘要：

```
$s0 = "2d3915cdc82e9093…" // sha256   ← RT_ICON payload 摘要
$s1 = "46dc088910439dad…" // sha256   ← 同左
$s2 = "64da33787b54a0d1…" // sha256   ← 唯一真实的样本哈希
condition: any of them
```

**为什么它比原形更难发现**：样本自己的哈希**也在**规则里，所以 `any of them` 照样命中，
「规则能不能用」这个自检完全通过。错误只体现在「另外五条断言了它们不是的东西」。
同一个子串判据还被复制到了正文的 IOC 速查表，于是 5 个对象摘要在「文件 SHA-256」标签下印刷。

**辨认特征**：

- 报告里同一类指标（`sha256`）的**条数多于**样本实际的文件身份数（正常是 3：md5/sha1/sha256）。
- 「文件哈希」标签下的值，在文档其他位置以「对象摘要 / 资源载荷」身份出现。
- 代码里存在**两个**回答「这是不是文件哈希」的谓词（本项目的病根：选择用一个、命名用另一个）。

**证实 / 证伪所需**：按**分隔符切词**后比较词元，而不是子串：

```python
_FILE_HASH_TOKENS   = {"file_identity", "content_sha256"}
_OBJECT_DIGEST_TOKENS = {"embedded_object", "decoded_artifact", "resource", "bytes_read", ...}
def _is_file_hash_source(source):
    tokens = set(re.split(r"[/:\\|]+", source.casefold()))
    if tokens & _OBJECT_DIGEST_TOKENS: return False     # 否决优先
    return bool(tokens & _FILE_HASH_TOKENS)
```

子串无法表达 `artifact` 与 `decoded_artifact` 的区别。而且**全项目只允许一个这样的谓词**：
正文渲染、规则投影、正确性核验三处必须调用同一个函数，否则修复会只落在其中一处。

## EC-6 把静态观察写成运行时事实（overclaim）

**错误形态**：把静态观察、隔离模拟结果、或推测写成目标主机上已发生的事实。本项目已有
`product_certification.static_wording_violations` 覆盖词汇层面；本判据覆盖**结构**层面：
词汇上合格但结构上仍在过度主张。

**报告里的辨认特征**：

- 机制状态是 `CANDIDATE` / `未过验证器`，但结论段用肯定句复述它。
- `EMULATION_OBSERVED` 的结果被写成「样本执行了……」，没有指明是隔离模拟。
- 结论里的动词是完成时（下载了 / 创建了 / 写入了），而全文没有任何运行时观察。

**证实 / 证伪所需**：每条运行时断言要么能指向一次真实的隔离模拟观察并标注其边界，
要么必须降级为静态可能。本项目已建立的正确边界措辞可以对照：
「隔离模拟观察（`EMULATION_OBSERVED`）不是目标主机上的运行时执行，也不是感染结论。」

**实测出处**：`product_certification.static_wording_violations` 的存在本身；
round 78 把 `WinHTTP export not found` 从「下载相关 API 名称」纠正为「解析/恢复失败结果」，
属于同一族（把解析器的失败读成样本的能力）。

## 审查纪律（与 `review` skill 同构）

- **各判据独立成报告，不合并、不重排**。一条发现只能挂在一个 EC 下；跨 EC 的发现分别列两次，
  因为它们的证伪条件不同。
- **每条发现必须指名出处**：`文件:行` 或 `revision id` + 可复制的原文片段。没有出处的发现不算发现。
- **区分硬错误与判断题**：IOC 值不等（EC-5）、计数对不上（EC-4）是硬错误；
  「这个 join 够不够强」（EC-3）常常是判断题，必须标出来。
- **禁止把「没找到」写成「不存在」**。审查者自己受 EC-1 约束。
- **给出可执行的下一步**：每条发现要写「补什么证据能消掉它」，而不是只说「这里有问题」。
