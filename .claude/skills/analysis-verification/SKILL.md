# analysis-verification — 分析结论正确性核验

## 这个 skill 解决什么

「事实在不在报告里」和「事实对不对」是两个问题。本项目已经有一个存在性验收
（`.scratch/check-report-acceptance.py`，24 条断言），它在正式正文上跑 24/24；**同一个正文里**
却有一条永远匹配不到本样本的 YARA 规则：

    $s0 = "0b05c0df699028e6cfc4c02147e91b7a4ecbc79569004caaf550ebcdb25c63a3" // sha256  ← 规则名后缀（自指）
    $s5 = "168d16f912e21ee7d521f5d0a59b08f96161b9e5b98aae21f6d5e0d7ca8a0db6" // sha256  ← RT_ICON[5] 摘要
    样本真实 SHA256 = 6bb6bfcbe68de69077b567789d5970c6613b1d4fb89becc4cf7a2f9a49861145

存在性检查看不见这个错误，因为两个字符串**确实**在正文里。正确性检查看得见，而且是机械可判的。
本 skill 就是那层检查。

## 何时使用

- 一份报告要发布 / 已发布，需要确认结论无误。
- 报告里出现归因、家族判断、C2、持久化、注入等**主张**。
- 报告里有可部署的 IOC / YARA / EDR 规则。
- 用户问「这个结果有没有问题」「能不能信」。

## 两层结构

### 第一层：机械核验（先跑，成本近乎为零）

```bash
py ".scratch/verify-report-correctness.py" <task_id>              # 正式 revision 正文
py ".scratch/verify-report-correctness.py" <task_id> --revision <id>
py ".scratch/verify-report-correctness.py" <task_id> --json       # 给程序消费
```

退出码 1 = 有 ERROR 级发现。它只做**可判定的**检查：每条声明都要能对上流水线已经记下来的证据。

| 判据 | 机械检查做什么 |
|------|---------------|
| EC-5 坏 IOC | 规则里每个标 `sha256` 的值必须等于 `file_identity.sha256`；不等就要能指出它是哪个内部对象的摘要，否则报 ERROR/WARN。规则名后缀自指单独报错。`url`/`ipv4`/`registry_subkey` 必须能在恢复到的字符串/解码结果里原样找到（比较前先还原 YARA 转义）。 |
| EC-4 静默截断 | 正文写「共 N 条」但同段只列了 M 项，**且该行没有说明自己是有上限的**，才报。已经写明边界的行不报。 |
| EC-6 过度主张 | 直接调用产品自己的 `product_certification.static_wording_violations`，保证只有一个定义。 |

机械层**故意不实现** EC-1 / EC-2 / EC-3：这三类的判据是「证据图里有没有那个消费者 / 那条例外」，
不是词法特征。EC-2 曾用词法实现过一版，在真实正文上产出 12 条发现、**12 条全错**（全是写好了边界的
静态主张），因此撤掉——误报率 100% 的检查比没有检查更糟，它训练读者忽略这个工具。
完整记录在 `.scratch/verify-report-correctness.py` 的 EC-2 注释里。

### 第二层：证据图核验（模型驱动，机械层查不了的三类）

按 `METHODOLOGY.md` 的 EC-1 / EC-2 / EC-3 逐条走。每条判据独立成报告，**不合并、不重排**
（与 `/review` skill 的两轴同构：一轴合格不能掩盖另一轴失败）。

**EC-1 缺席当证明** — 报告里任何归属结论，问一句：正面证据是什么？
- 只有「不在 X 列表里」→ 错误。`peinfo` 记录的 `61110bea` 误归因就是这么来的。
- 拿不到正面证据 → 只能是 `UNKNOWN(attribution)`。

**EC-2 字符串当行为** — 任何行为句，问一句：消费者是谁？
- 要给出调用点 / 参数位 / 寄存器来源 / 对象级使用链。
- 给不出 → 必须写成「镜像内字符串线索」并标注边界。
- 正面样板（本项目已做到的写法）：`FoxitPDFReader.exe` 被写成「镜像内字符串线索，未恢复到对应的
  进程创建参数，因此不能当作已恢复的命令行」。

**EC-3 错误 join** — 任何 join，问一句：这条 join 落在哪条指令上？
- 调用点↔参数、写入↔持久化、URL↔参数位，三种最常见的连错法见 `METHODOLOGY.md`。
- join 必须在**同一函数窗口内**有指令级证据。拿不到就写 `UNKNOWN(槽位)` + 具体卡点
  （哪条指令、缺什么），禁止用套话收尾。

## 输出格式

每条发现写四样：`判据` / `严重级` / `出处（文件:行 或 revision id + 可复制原文）` / `补什么能消掉它`。
没有出处的发现不算发现。区分**硬错误**（IOC 值不等、计数对不上）与**判断题**（join 够不够强）。

最后给一行总账：每条判据各几条、最严重的一条是什么。

## 审查者自己受同样约束

- **不得把「我没找到」写成「不存在」**——这是 EC-1，审查者自己也犯。
- 不用「未提供对象级使用链」这类套话收尾；写清缺哪个槽位、卡在哪条指令。
- 检查报告是不是把**有上限的清单**写成了全集（EC-4）——这正是审查者最容易漏的一类，
  因为每条事实都真，假的是「完整性」这个断言。
