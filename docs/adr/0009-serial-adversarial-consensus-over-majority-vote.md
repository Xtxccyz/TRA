# 使用串行对抗共识而非多数投票

参考SentinelOne的Adversarial Consensus Engine，本项目采用“确定性提取—串行分析—主动拒绝—复核轮—报告合成”的对抗流程。每个后续验证者读取带版本的共识上下文，必须对前序Claim标记AGREE、DISAGREE或N/A，并给出证据锚点与拒绝理由；第二轮以不同顺序或不同验证职责重新检查重要和争议Claim。只有通过复核且具有独立证据来源，或具有不可争辩的直接证据，Claim才可提升状态；多数Agent的一致意见不能代替独立证据。

一期先以确定性静态提取和Ghidra为主要来源，任何同源的多模型复核都标记为同源语义挑战，不冒充多工具共识；IDA和Unicorn接入后再增加真正独立的静态与动态来源。对单个Claim的复核保持串行，对互不依赖的Artifact分支可以并行。

## Consequences

拒绝记录、共识上下文版本、验证顺序和每轮输出必须进入追溯链。第二轮只消费经过提炼的Claim和争议记录而非重复解析全部原始输出，以控制上下文和成本；确定性Bridge负责全量提取，避免Agent因没有提出某个查询而漏掉基础事实。

Gauntlet按风险路由：解密、加载、注入、持久化、C2、窃密、反分析、重要ATT&CK映射和归因等高价值Claim强制进入完整对抗轮；低风险确定性事实只做Schema、证据锚点与可复现性校验，发生冲突或成为关键结论依赖时再升级。

验证门槛同时按风险分级：哈希、文件结构等T0事实可由确定性复现确认；解密、加载、注入和C2机制等T1结论需要独立来源或专家提供带证据锚点的复核；ATT&CK正式映射、活动/组织归因和外部发布等T2结论需要多源证据及人工Gate。静态Claim即使通过验证，也不得被表述为运行时行为已实际发生。
