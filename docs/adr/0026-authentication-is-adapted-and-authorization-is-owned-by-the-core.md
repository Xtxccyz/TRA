# 认证可替换，授权由核心系统负责

核心系统通过Auth Adapter验证OIDC/JWT并形成标准Principal，不绑定特定平台的账号目录；第三方调用使用具有明确权限范围的Service Account。核心RBAC定义Analyst、Reviewer、Operator、Auditor和Admin角色及细粒度权限，所有Case操作、Gate裁决、Report Revision编辑和批准都由API服务端授权并记录实际Principal。

## Consequences

同一用户一期可以兼任多个角色，但审计仍保留每次动作使用的身份与权限。受限审计载荷默认只允许Auditor读取；Analyst和Reviewer只能查看结构化分析结果与上下文清单，Admin的系统管理权限不自动包含案件正文读取权限。非Auditor的临时读取必须通过应急审计访问：由拥有audit_access.grant权限的Admin批准，申请人与批准人不得相同，且授权限定理由、对象范围与最长24小时有效期并逐次审计。Case证据销毁采用三方职责分离：申请人不得复核或执行自身请求，Reviewer持有evidence_purge.review并核对影响，另一名Admin持有evidence_purge.execute并授权保留服务执行。保留冻结可由Reviewer或Auditor创建和延期，解除由不同Principal的Admin批准；冻结不会授予正文读取权限。Docker Compose可显式启用带醒目标识的single-user demo mode；该模式可以放宽职责分离，但每个例外必须显式标记，正式部署配置必须关闭。未来平台只需提供兼容OIDC/JWT或实现新的Auth Adapter，不改变领域权限和审计契约。
